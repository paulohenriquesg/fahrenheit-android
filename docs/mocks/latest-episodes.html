Latest Episodes — giving the list something to say

Today it is a flat list of covers and titles with no dates, so an episode from this morning looks exactly like one from March. That is most of why it felt stale. The server already orders by publishedAt and we now read it — this is what it can show once it does.

1. Grouped by when, with what is new marked

Days do the sorting work the eye wants: Today, Yesterday, then the week, then dates. Each row carries its duration and, if you have started it, how far in you are — on the artwork, where the eye already is. A row is one focus stop; the centre button plays it.

2. Empty, and honest about why

The list can be empty for two very different reasons and today says the same thing for both. The server returns only unfinished episodes, so a diligent listener empties it — that is not an error and should not read like one. The other reason is the one you just hit: nothing is being fetched, because a podcast has auto-download off and its feed has not been checked in two years.

What this needs from the code

  • Already done (in #70): publishedAt parsed, and the row says Today / Yesterday / 4 days ago / a date.
  • Small: group the rows by day, and mark anything from the last day or two as New. Pure function over the list, easy to test.
  • Needs more fields: duration and progress are not in RecentPodcastEpisode — the server sends audioFile.duration and the user's media progress separately. Worth one audit of the real response before designing against it, the way the DTO audit was done.
  • The empty state needs to know when the server last checked, which is per podcast (lastEpisodeCheck) and not in this response at all. Possibly worth leaving as the plain "all caught up" line until that is cheap.
  • Open question: should finished episodes be shown struck through rather than hidden? The server can return them with a different filter, and "where did it go?" is a fair complaint.
